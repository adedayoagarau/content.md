# Research gap register

This register separates a strong first desk-research foundation from questions that still need primary research, technical experiments, specialist review, or market evidence. “Open” does not mean optional; several gaps block a responsible public specification.

## Priority definitions

Research-gap priority uses an `RG-` namespace so it cannot be confused with the nonwaivable P0-A–G capability-phase gates in the [security study](../05-technology/security-privacy-and-trust-boundaries.md).

- **RG-P0 — blocks the core model:** resolving this could materially change the ontology, evidence/control and decision-rights model, safety boundary, or minimum workflow.
- **RG-P1 — blocks a credible v1 capability:** the core can be modeled, but a product promise or adapter should not ship without this evidence.
- **RG-P2 — informs expansion or governance:** important for scale, adoption, and ecosystem health after the narrow end-to-end proof.

## Minimum research sequence

1. Run exploratory interviews and artifact walkthroughs while modeling real decisions.
2. Independently review the cognitive-ergonomics claims and context packet; retain myths, nulls, contradictions, cultural/accessibility limits, prohibited influence, and unsupported transfer rather than turning recurring effects into rules.
3. Build the first message-in-context ontology from real artifacts, not from abstract brainstorming alone.
4. Create two instrumented reference products: one greenfield and one inherited, with deliberate conflicts, missing facts, locales, accessibility states, cognitive/influence adversarial cases, and dead strings.
5. Validate the P0-A–G gate threat/control model, complete product-specific privacy/data-flow and provider decisions, implement connector authorization/revocation and package/update controls, and pass the relevant release gates before enabling each new capability—especially writes and controlled runtime verification.
6. Implement discovery and read-only planning before any write capability.
7. Build expert-adjudicated, malicious-repository, prompt-injection, data-leak, controlled-claim, cognitive-myth, safe-counterexample, and manipulative-influence benchmark sets.
8. Test a single journey through discover, model, plan, and approve; make apply phase-eligible only after safe round-trip and P0-D/E pass, and make executable verification phase-eligible only after the exact `verify.runtime` profile passes P0-G. Every actual apply or verification task still requires an independently constructed least-privilege grant for its exact actor, operation, resource, data/credential/filesystem/network boundary, environment, and expiry, plus every applicable current connection-authorization, data-processing, durable-memory, and telemetry record or an explicit not-applicable rationale. Mutation also requires mandatory mutation/change approval, releasable content and enforceable rules require applicable semantic decision approval, and release requires a separate release approval when policy requires residual-risk acceptance.
9. Run specialist reviews for scientific validity, cognitive accessibility, locale/culture, domain risk, privacy, security, ethics, safeguarding, and affected-user safety.
10. Only then stabilize the minimum repository contract and public compatibility promise.

## Completion rule

No number of additional style guides closes an RG-P0 gap by itself. Close a gap only when the stated method has been run, its evaluated results meet a predefined close criterion, limitations and counterevidence are recorded, and the accountable role makes a scoped close decision. An inspectable artifact and evidence record are necessary, but their existence alone is not a successful or conclusive result.
