## T1 Navigation & IA labels

**Global nav is five items, and the first one is a verb** `[observed]`

`Build` · `Product` · `Solutions` · `Library` · `Pricing`, plus a language switcher, `Sign up`, `Login`, and `Let's connect`.

Naming the developer-resources menu `Build` rather than "Developers" or "Resources" is the notable choice: the top-level label is the developer's activity, not their job title. `Library` for the content marketing hub is the other unusual one — a bookish noun where most sites say "Resources".

**Each mega-menu is grouped by small-caps section headings, and the groupings differ in kind per menu** `[observed]`

- `Build` → `Documentation` · `Quickstarts` · `Developer Tools` · `Connect`
- `Product` → `AI IDENTITY` · `CUSTOMER IDENTITY` · `ENTERPRISE CONNECTIVITY` · `AUTHORIZATION` · `PLATFORM & EXTENSIBILITY`
- `Solutions` → `USE CASES` · `WHO IT'S FOR` · `TRENDING`
- `Library` → `EXPLORE BY TOPIC` · `EXPLORE BY TYPE` · `EDUCATION`

`EXPLORE BY TOPIC` / `EXPLORE BY TYPE` is the cleanest pair on the site — the same content inventory offered on two axes, with the axis named in the heading so the reader knows which question each column answers. Compare `WHO IT'S FOR`, which is a good plain-English heading for a vertical list (`Financial Services`, `Healthcare`, `Retail`) but then includes `Partners`, which is not a "who it's for" at all.

**`Developer Tools` is a standalone-tool inventory, and every item leaves the site** `[observed]`

`JWT Decoder↗` (jwt.io) · `Webauthn Demo↗` (webauthn.me) · `OIDC Playground↗` (openidconnect.net) · `SAML Tool↗` (samltool.io) · `Passkeys Playground↗` · `Auth0 Deploy CLI↗` · `Auth0 Status↗`

Seven free tools, none on the auth0.com domain, all marked with `↗`. Auth0 has built and named a set of **protocol-debugging utilities under generic domain names** and links to them as if they were third-party. That is a content-and-distribution strategy: the tool ranks for the protocol, not for Auth0. The `↗` affix is applied consistently across all external links in the nav (also `Community↗`, `Knowledge Base↗`, `Marketplace↗`, `Auth0 Learning↗`), so the reader always knows when they are leaving.

**Footer groupings are named by the reader's stage, not by the company's org chart** `[observed]`

`STARTING WITH AUTH0` · `DOCUMENTATION` · `CONTACT & HELP` · `COMPANY & TRUST`

`STARTING WITH AUTH0` as a footer heading is doing onboarding work in the footer — it contains `Intro to IAM`, `Auth0 platform`, `Auth0 features`, `Pricing`, `Get started for free`, i.e. the evaluation path in order. `COMPANY & TRUST` bundles the ownership disclosure: every link in it except `Partners` points at `okta.com` or `security.okta.com`.

**Support Center IA: four cards, each with a scope line and three seeded links** `[observed]`

| Card | Scope line (verbatim) |
|---|---|
| `Get Started` | "Learn the basics to begin using Auth0" |
| `Troubleshoot` | "Access resources to resolve common issues" |
| `Account Management` | "Find answers and resources related to managing your Auth0 account" |
| `Connect` | "Engage with the community and share best practices" |

Each card exposes three example articles rather than a category link alone, so the reader can judge the category's contents before clicking. The `Troubleshoot` card's three seeds are the most-searched failures, and one of them quotes a literal error string in its title: `"User Already Exists" Error When Creating New User`.

**Docs URL structure is itself an IA statement** `[observed]`. Auth0's docs paths are verb-first at the top level: `/docs/get-started/`, `/docs/authenticate/`, `/docs/manage-users/`, `/docs/customize/`, `/docs/secure/`, `/docs/deploy-monitor/`, `/docs/troubleshoot/`, plus noun-based `/docs/libraries/`, `/docs/api/`, `/docs/quickstarts/`, `/docs/glossary`. **Seven verbs and four nouns**, with the verbs describing what the developer is doing to the identity system and the nouns describing reference material. A reader can guess a URL from an intent, which is the practical test of this kind of IA.

Note that `/docs/troubleshoot/...` URLs now **redirect to `support.auth0.com`** — the troubleshooting branch of the docs tree has been migrated to a Salesforce-hosted support site while retaining the docs URL shape. See T11 and Caveats.

## T2 Value proposition & headline patterns

**Hero: three verbs, one object** `[observed]`

> Headline: `Convert, protect, & personalize every journey`
> Subhead: "Auth0 makes every login effortless, so fewer customers walk away. It stops fraud behind the scenes and keeps users recognized across your sites, apps, and AI-assisted touchpoints."

The headline is a **verb triplet with an ampersand**, and the three verbs are then reused as the labels of the lifecycle tab set below (`Convert` / `Protect` / `Personalize` / `Grow`). Headline and navigation are the same four words, which is the same trick Wise uses with `Cheapest way` / `Fastest way`.

Two things in the subhead are worth recording. `so fewer customers walk away` frames identity as a **conversion loss**, not a security gain — the business metric first. And `stops fraud behind the scenes` is the only claim in the hero addressed to the security buyer, deliberately positioned as invisible ("behind the scenes"), which is how a CIAM vendor sells friction reduction and fraud prevention in the same breath.

**The lifecycle model is rendered as two parallel eight-stage journeys** `[observed]`

`Identity for the entire customer lifecycle`, with a `B2C` / `B2B` toggle. Each stage pairs a **journey moment** with a **business verb**:

| B2C moment | Verb | B2B moment | Verb |
|---|---|---|---|
| `Sign up` | `Convert` | `Evaluation` | `Win` |
| `Login` | `Protect` | `Onboarding` | `Accelerate` |
| `Checkout` | `Personalize` | `Expansion` | `Scale` |
| `Agentic Experience` | `Grow` | `Agentic Readiness` | `Evolve` |

**This is the strongest structural content pattern on the site.** The moment names are what the *end user* does; the verb names are what the *buyer* gets. Every panel then opens by repeating its own verb as the first word of the sentence — "Convert more customers through secure and easy sign up." · "Protect revenue by stopping fraud without adding unnecessary friction." · "Win. Close deals faster with enterprise grade identity…" · "Accelerate time-to-value by removing onboarding friction so customers go-live faster." A reader can skim only the verbs and get the whole pitch; a reader who stops on one panel gets the mechanism.

Note `Agentic Experience` (B2C) versus `Agentic Readiness` (B2B) — the same new capability named as an *experience* for consumer products and as a state of *preparedness* for enterprise buyers. One feature, two nouns, chosen per buyer's anxiety.

**Audience tab headers are imperative and each names a fear** `[observed]`

- `Ship AI agents faster, without losing control`
- `Drive sign-ups with frictionless authentication` — body opens "Don't let a clunky login screen block growth and revenue."
- `Build enterprise-ready auth without the headache` — body opens "Stop burning sprints on custom SAML just to close a contract."
- `Secure machine identities & APIs at scale` — body opens "Don't let long-lived API keys and sprawling service credentials become a compliance liability and attack surface."

**Three of the four bodies open with a negative imperative** (`Don't let…`, `Stop burning…`, `Don't let…`), each naming a specific engineering indignity in the reader's own words: *a clunky login screen*, *burning sprints on custom SAML just to close a contract*, *long-lived API keys*. This is the house device — **lead with the thing the reader hates, then the capability list.** "Stop burning sprints on custom SAML just to close a contract" is the single best sentence on the site: it names the task, the cost unit (sprints), and the humiliating reason (to close a contract).

**Section headers elsewhere** `[observed]`: `Built for what you're building` · `Built for industries that can't afford to slow down` · `Integrate auth into any stack in minutes` · `You're in great company` · `Read. Watch. Code. More.` · `Get ready to ship at the pace of AI`.

`Read. Watch. Code. More.` is a four-word header whose fourth word breaks its own pattern (three verbs then a quantifier) — recorded as a deliberate but slightly awkward construction. `Built for…` used twice as an anaphora two sections apart.

**Trust stats are given with attribution and a caveat footnote** `[observed]`

- `3 billion+` / "attacks blocked each month*" — footnote: "*by Okta (Auth0 and Okta platforms)"
- `99.99%` / "uptime" — footnote: "*12-month availability, as indicated at trust.okta.com"
- `23 billion+` / "authentications every month"

The first two carry **claim-bounding footnotes in the Wise style**: the attack figure is disclosed as *combined Auth0 + Okta*, not Auth0 alone, and the uptime figure is attributed to an external page with the measurement window stated. The third (`23 billion+`) has no footnote and no window — an inconsistency in an otherwise disciplined stat block.

**Pricing headline** `[observed]`: `The first and last auth platform you'll ever need`, subhead "Flexible pricing for all your apps and AI agents from user 1 to 1,000,000+". The `from user 1 to 1,000,000+` construction states the range rather than the price, which is honest for a MAU-metered product where no single number is meaningful.

**An agent-readiness metric presented as a product claim** `[observed]`: "98% Agent Experience Score as measured by Auth0 Evals", beside a simulated terminal session showing `/plugin install auth0@claude-plugins-official` and `>Add Auth0 login to this app`. Auth0 has coined a **self-measured score for how well AI coding agents can use its product**, named the measuring instrument, and put the number on the homepage. Self-attributed but disclosed as self-attributed.

## T4 Onboarding & getting-started

**The onboarding surface is a framework grid, not a sequence** `[observed]`

`Integrate auth into any stack in minutes` — "Use our 30+ SDKs and Quickstarts to integrate auth into any language or framework." The nav then shows six named quickstarts with logos (`React`, `Next.js`, `Angular`, `Vue.js`, `React Native`, `iOS / Swift`), a scope line — "Build in 30+ of your favorite languages & frameworks" — and `View all Quickstarts→`.

The quickstart URL pattern encodes an **application-type taxonomy** that is itself the onboarding IA: `/docs/quickstart/spa/react/`, `/docs/quickstart/webapp/nextjs`, `/docs/quickstart/native/react-native`. Three app types — `spa`, `webapp`, `native` — crossed with framework. The developer picks *what kind of thing they are building* before *what they are building it in*, which is the correct order because the auth flow differs by app type and not by framework. One of the six (`react`) carries an `/interactive` suffix, so at least one quickstart has a distinct interactive variant.

**The 2026 onboarding story is an agent-installed integration** `[observed]`. The homepage shows a tabbed terminal for `Claude` · `Cursor` · `Codex` · `Antigravity`, with the transcript:

> `$/plugin install auth0@claude-plugins-official ✓ detected`
> `>Add Auth0 login to this app`
> `Linstalling @auth0/nextjs-auth0 ✓`
> `Lwiring routes + login ✓`
> `✓Auth0 is live ∙ ready in 4.2s`

**The onboarding copy has been reduced to one natural-language instruction** (`Add Auth0 login to this app`) plus three machine-authored progress lines. Note that the progress lines are gerund-initial and terminated with a check (`installing … ✓`, `wiring routes + login ✓`) and the completion line states both a state and a duration (`Auth0 is live ∙ ready in 4.2s`). This is a preview of where getting-started content goes when the reader is an agent: the human-facing string is the prompt, and the rest is a log.

**Docs "Before you start" cards are a real prerequisite pattern** `[observed]`. `Customize Signup and Login Prompts` opens with a `Before you start` card containing three numbered, verifiable conditions:

1. "Make sure your tenant has a **Custom Domain** configured."
2. "Confirm you are using **Universal Login** for all signup and login prompts, and ensure the **Customize Login Page** toggle has been disabled for Login Prompts."
3. "Check that you have a Custom Page Template configured."

Each item starts with a different checking verb (`Make sure` / `Confirm` / `Check`), each names the exact setting, and item 2 includes a **negative prerequisite** (a toggle that must be *off*). Prerequisites-as-a-card at the top, before any concept, is applied consistently enough across Auth0 docs to read as a template.

**Recommended-setup content is written as a to-do list with the reason attached to each item** `[observed]`. `Tenant Settings` opens with `Recommended settings` — "When you configure your tenant, set the following items:" — eight bold imperatives each followed by the consequence:

- "**Specify the Environment Tag.** Tenants tagged as **Production** are granted higher rate limits…"
- "**Set the Support Email and Support URL.** If a user encounters an issue while logging in, they'll want to reach out for help. Set these values to direct them to an email address or landing page to get assistance."
- "**Configure a custom error page.** If possible, you should host your own custom error page… This allows you to provide more complete and customized explanations to users about what to do in the event of an error."
- "**Disable the Enable Application Connections setting.** If this setting is enabled, all configured connections will be automatically enabled for any new application you create. As a result, users may be able to log in to the application through connections that you did not intend to be available."

Three of these are load-bearing for content design and are analysed in T7: the Support Email/URL item is Auth0 telling the *developer* that the *end user* will need a human, at setup time; the custom-error-page item is Auth0 telling the developer that Auth0's own default error page is deliberately uninformative; and the `Enable Application Connections` item is a **recommendation to turn a default off**, with the security consequence spelled out. A vendor recommending against its own default, in its own setup checklist, is an unusual and creditable content decision.

| `Logo URL` | "URL of the logo you want to be displayed on the Universal Login page. Minimum recommended resolution is 200 pixels (width) by 200 pixels (height)." |

| `Default Language` / `Supported Languages` | "Language your tenant will use by default." / "Languages also supported by your tenant." |

| `Allowed Logout URLs` | "URLs Auth0 can redirect to after logout when no client_id is specified…" |
| `Inactivity timeout` | "Timeframe (in minutes) after which a user's session will expire if they haven't interacted with the Authorization Server." |
| `Require log in after` | "Timeframe (in minutes) after which a user will be required to log in again, regardless of their activity." |
| `User Code Character Set` / `User Code Mask` | "Mask used to format the user code… allowing spaces or hyphens for readability." |

**`Friendly Name` is the field name worth stealing.** It is not "Company name" or "Display name" — it names the *quality the value must have* (friendly, i.e. human-readable, i.e. what a stranger would recognise), and the help text then supplies the likely answer ("Typically this is the name of your company"). A field label that specifies a property of the value rather than its category.

**`Inactivity timeout` / `Require log in after` is the other one.** Two session settings that developers routinely confuse, disambiguated by making one a noun phrase about the *user's* inaction and the other an imperative about the *system's* obligation, with the distinguishing clause in each help text ("if they haven't interacted" versus "regardless of their activity"). The help texts are written to be read as a pair.

**Toggle-style settings are written as full declarative sentences beginning "When enabled, …"** `[documented]`, consistently across the Advanced tab: "When enabled, third-party developers will be able to…", "When enabled, errors generated while using the public signup API will return a generic response.", "When enabled, it deletes the underlying grant when you revoke a refresh token…", "When enabled, all current connections will be enabled for any new application that is created."

The `When enabled, …` frame is applied to ~10 consecutive settings. It resolves the perennial toggle problem (does the label describe the on state or the action?) by never describing the toggle at all and always describing the resulting world.

**Attack Protection section labels form a three-part model** `[documented]`, identical across Brute-Force Protection and Breached Password Detection: `Detection` → `Response` → `Notifications`. Inside them:

- Detection: `Breached Password Detection Method`, with the two option strings `When breach data is published` and `As soon as possible based on data received from the dark web, with Credential Guard`; brute-force `Default` (10) / `Custom` (1–100); `IP AllowList`
- Response: `Block Brute-force Logins` · `Account Lockout` · `Block compromised credentials for new accounts` · `Block compromised user accounts` · `Block compromised credentials use for password reset`
- Notifications: `Send notifications to the affected users` · `Send notifications to users with compromised credentials` · `Compromised user accounts` · frequency options `Immediately` / `Daily` / `Weekly` / `Monthly`

**The `Detection` → `Response` → `Notifications` triad is the transferable artefact.** Every attack-protection feature uses the same three section names in the same order, so an administrator configuring the fourth feature already knows the shape. And the option strings are *outcome sentences*, not adjectives: `Block compromised credentials for new accounts` versus `Block compromised user accounts` versus `Block compromised credentials use for password reset` — three toggles distinguished by naming the moment in the lifecycle each one guards. (The third is ungrammatical — "credentials use for" — a defect in an otherwise careful set.)

**A real duplicate-label defect** `[documented]`: in the Breached Password Detection notification steps, `Compromised user accounts` is given as the label for **two different toggles** — step 4 ("send an email to administrators when a user signs up with compromised credentials") and step 5 ("…when a user logs in with compromised credentials"). Two distinct events, one label, in consecutive numbered steps of the same procedure.

**Universal Login form-element support and its validation contract** `[documented]`: supported inputs are enumerated as literal HTML (`<input type="text">`, `"number"`, `"checkbox"`, `"password"`, `"email"`, `"tel"`, `"url"`, `<select>`, `<textarea>`), with class hooks `ulp-field`, `ulp-error`, `ulp-error-info` and data attributes `data-ulp-validation-function`, `data-ulp-validation-event-listeners`. Custom input names must carry a `ulp-` prefix "to ensure the data is available to Actions".

## T6 Status & state language

**Status page is region-first, not service-first** `[observed]`

Roll-up headline: `All Regions Operational` — note **Regions**, not "Systems". The page then lists ten named regions, each with its own status icon: `US-1` · `US-3` · `US-4` · `US-5` · `EU-1` · `EU-2` · `AU` · `JP-1` · `UK-1` · `CA-1`.

Selecting a region gives a nested roll-up in a different vocabulary: `US-1 : All Systems Operational`, then `Current Status: **Operational** | Last updated at September 21, 2026, 2:14 UTC`, then `Past 12 months: 99.99% uptime`, then two service groupings: `Core Services` and `Supporting Services`.

**Three things are notable.** The gap numbering (`US-1`, `US-3`, `US-4`, `US-5` — no `US-2`) is left visible rather than renumbered, which is correct: customers are provisioned into named regions and renaming them would break every runbook. The **`Core Services` / `Supporting Services` split** tells a customer whether a degraded component is on their critical path without them needing to know the architecture. And `Past 12 months: 99.99% uptime` is shown per region on the status page itself, so the SLA figure sits beside the live state rather than only in a sales table.

**State vocabulary** `[observed]`: `Operational` · `Service Disruption` · `99.99% Uptime` (as a legend key) · and a checkbox `Show Minor Incidents`.

`Show Minor Incidents`, **unchecked by default**, is a genuinely interesting decision to record: the page hides its own smaller failures behind an opt-in. Defensible (signal-to-noise for the operator glancing at a dashboard) and also exactly the kind of default that erodes trust when discovered. Note also that the severity vocabulary here is two-valued (`Operational` / `Service Disruption`) plus a `Minor` tier reachable only via the checkbox — much coarser than the five-state Statuspage legends used by DigitalOcean and Retool.

`Auth FGA status` is a **separate status page** (`status.fga.dev`), linked from the header — one product family, two status domains.

**Attack-protection status indicator is three-valued, and the third value is the clever one** `[documented]`

> "The current state is shown in the **Enabled** / **Disabled** status indicator." … "If you enable brute-force protection but disable all response settings, the status indicator changes to **Monitoring** and Auth0 records attack protection events in your tenant log but takes no further action."

`Monitoring` is a **derived state**, not a setting: it appears when the feature is on but every response is off. Rather than letting an administrator believe they are protected, the indicator changes its own label to describe what is actually happening. The same wording recurs on Breached Password Detection: "Enabling attack protection features without any response settings enabled activates Monitoring mode, which records related events in your tenant log only."

**This is the best status-language pattern in the file.** A configuration that is technically "enabled" but functionally inert gets its own honest third label. Directly transferable to any product with an enforce/observe/off axis — fraud rules, content filters, firewall policies, feature flags.

**Signing-key states are named by position in a rotation queue** `[documented]`

`Next in queue` ("Key that will be used when the signing key is next rotated") · `Currently used` ("Key that is currently in use") · `Previously used` ("Key that was previously used. Its appearance indicates that the signing key has been rotated, but the previously-used key has not yet been revoked.")

The `Previously used` definition ends by telling the reader what the state's *presence* means, not just what it is — the state is a diagnostic signal. Paired with two distinct actions whose labels encode their consequence: `Rotate Signing Key` ("Rotates the signing key without revoking it") versus `Rotate & Revoke Signing Key`, with a warning attached to the destructive one ("Make sure you have updated your application with the next key in the queue before you rotate and revoke the current key").

**Block-lifecycle states** `[documented]`: brute-force blocks "remain in effect until one of the following events occurs" — five named exits (30 days elapsed, admin unblock via API, threshold raised, user clicks the unblock link, user changes password). A block is documented as a state with an enumerated exhaustive exit list, which is what an administrator on a support call needs. Tenant-administrator blocks are explicitly called out as "handled separately from brute-force protection blocks" — two similar-looking states distinguished because their removal paths differ.

**Log event type names** `[documented]`: `pwd_leak` · `signup_pwd_leak` · `reset_pwd_leak`. Three events for one condition, prefixed by the flow in which it was detected. Also referenced: `type: "signup_pwd_leak"` as a literal log-search query the docs tell you to run.

**Rendering modes for login screens** `[documented]`: `STANDARD` · `ADVANCED` · `ADVANCED (FILTERED)`, each defined by what it does to customisation ("partials do not apply", "partials only apply to `screens` excluded from ACUL filters").

## T7 Error, failure & recovery

**This is the richest section in this file, and the assigned focus.** Auth0 publishes both halves of the split: a **specific developer-facing error-code vocabulary** and a **tenant setting that deliberately collapses it** for end users, with the reasoning stated.

### The developer-facing error-code reference `[observed]`

From `Common Auth0 Library Authentication Errors` — "Here is a list of the most common errors that you might get if you use any of the Auth0 libraries for authentication."

**Sign-up errors** — eight codes, each with a one-clause description:

| Code | Description (verbatim) |
|---|---|
| `invalid_password` | "If the password used doesn't comply with the password policy for the connection" |
| `invalid_signup` | "The user you are attempting to sign up is invalid" |
| `password_dictionary_error` | "The chosen password is too common" |
| `password_no_user_info_error` | "The chosen password is based on user information" |
| `password_strength_error` | "The chosen password is too weak" |
| `unauthorized` | "If you cannot sign up for this application. May have to do with the violation of a specific rule" |
| `user_exists` | "The user you are attempting to sign up has already signed up" |
| `username_exists` | "The username you are attempting to sign up with is already in use" |

**Log-in errors** — ten codes:

| Code | Description (verbatim) |
|---|---|
| `access_denied` | "When using web-based authentication, the resource server denies access per OAuth2 specifications" |
| `invalid_user_password` | "The username and/or password used for authentication are invalid" |
| `mfa_invalid_code` | "The multi-factor authentication (MFA) code provided by the user is invalid/expired" |
| `mfa_registration_required` | "The administrator has required multi-factor authentication, but the user has not enrolled" |
| `mfa_required` | "The user must provide the multi-factor authentication code to authenticate" |
| `password_leaked` | "If the password has been leaked and a different one needs to be used" |
| `PasswordHistoryError` | "The password provided for sign up/update has already been used" |
| `PasswordStrengthError` | "The password provided does not match the connection's strength requirements" |
| `too_many_attempts` | "The account is blocked due to too many attempts to sign in" |
| `unauthorized` | "The user you are attempting to sign in with is blocked" |

**The developer-facing half is deliberately granular.** Where a single user-visible outcome ("your password won't work") exists, Auth0 ships four distinct codes that tell the developer *why*: `password_dictionary_error` (too common), `password_no_user_info_error` (derived from the user's own data), `password_strength_error` (too weak), `PasswordHistoryError` (previously used). Similarly, MFA failure is split three ways by *whose* problem it is: `mfa_invalid_code` (user typed it wrong), `mfa_registration_required` (administrator's policy, user hasn't enrolled), `mfa_required` (normal next step, not an error at all). `mfa_required` appearing in an error table is itself informative — the flow's continuation is surfaced through the error channel.

`invalid_user_password` — **"The username and/or password used for authentication are invalid"** — is the load-bearing entry for this section. The `and/or` is the deliberate vagueness, *in the developer-facing description itself*. Auth0 does not tell the integrating developer which of the two was wrong, because doing so would let the developer build an enumeration oracle on top of Auth0's API. The vagueness is pushed down to the platform boundary rather than being left to the customer's front end.

### The deliberate-vagueness setting, stated with its reason `[observed]`

From `Tenant Settings` → Advanced → Settings, verbatim:

> **Use a generic response in public signup API error message**: "When enabled, errors generated while using the public signup API will return a generic response. This helps protect against user registration enumeration by preventing bad actors from being able to guess previously-registered identifiers (username, email, or phone) from reading error response codes, such as `user_exists`."

**This is the cleanest published statement of the pattern in the corpus so far, and it has four parts:**

1. **The setting name states the mechanism** — `Use a generic response`, not "Enhanced signup security" or "Privacy mode". A developer reading the label knows exactly what will change about their error handling.
2. **The threat model is named** — "user registration enumeration".
3. **The adversary is named** — "bad actors", which is itself a glossary term with a tooltip definition ("Entity (a person or group) that poses a threat to the business or environment with the intention to cause harm").
4. **The specific code being suppressed is quoted** — "from reading error response codes, such as `user_exists`." Auth0 names the exact string it is hiding, in the documentation of the feature that hides it.

Point 4 is the subtle part. The documentation is **more specific than the product**: it publishes the code so the developer can reason about the trade-off, while the runtime withholds it so the attacker cannot. That is the correct distribution — the informative version lives where only authenticated administrators and readers of docs will find it, the vague version lives on the wire.

Note also that the setting is **off by default** (it appears in a list of settings a developer must actively consider, and does not appear in the eight `Recommended settings` at the top of the page). Auth0 documents the safer behaviour and ships the more debuggable one — a defensible choice for a developer platform, and a finding worth recording as such rather than as praise.

### The honest disclosure of a remaining enumeration surface `[observed]`

From `Brute-Force Protection`:

> "Brute Force Protection applies to login attempts only. If an identifier is blocked due to repeated failed login attempts, new users can still sign up with that identifier and receive a verification email."

This is a callout documenting a **known information leak created by the interaction of two features**: a blocked identifier is still signup-visible, and the verification email confirms it exists. Auth0 states it plainly, in a box, in the feature's own documentation, without minimising it and without a remediation. Disclosing the residual gap next to the protection is rare and is the kind of negative finding this corpus should record on the credit side.

### Guardian (MFA) error-code reference — 31 codes `[observed]`

The page's own framing states the intended use precisely: **"Use the error codes to display informative messages and to distinguish between recoverable and unrecoverable errors."**

That sentence is the design brief for the whole table. Selected entries showing the categories:

- **Wrong input, recoverable**: `invalid_otp` ("Provided otp code was not valid") · `invalid_recovery_code` · `invalid_otp_format` ("OTP format validation error") · `invalid_recovery_code_format` · `invalid_phone_number` ("The provided phone number is invalid")
- **Expired / stale, recoverable by restart**: `login_transaction_not_found` ("The mfa auth transaction is not active or has already expired") · `enrollment_transaction_not_found` · `transaction_expired`
- **State conflict, user-actionable**: `already_enrolled` ("You are already enrolled, cannot enroll again") · `not_enrolled` ("You not enrolled. Must enroll first") · `enrollment_conflict` ("There is another enrollment for the same user. You cannot enroll twice.")
- **Rate limited, with the scope named**: `too_many_sms` ("You have exeed the amount of SMSs assigned to your user") · `too_many_pn` · `too_many_sms_per_tenant` · `too_many_pn_per_tenant` — **four codes distinguishing per-user from per-tenant exhaustion**, which is exactly the distinction a support agent needs
- **Delivery failure, with cause where known**: `error_sending_sms` ("SMS Delivery error") · `error_sending_push_notification` ("Push notification delivery failed") · `push_notification_wrong_credentials` ("Push notification delivery failed because of wrong credentials")
- **Disabled, with *who* disabled it named**: `feature_disabled` ("The requested feature is currently globally not available (contact the provider)") versus `feature_disabled_by_admin` ("The requested feature is currently disabled by your admin") — **two codes for one symptom, split by whose fault it is and therefore who the user should ask**. Also `enrollment_method_disabled` and `auth_method_disabled`, each noted as carrying a `.method` field
- **Explicitly not-your-problem**: `tenant_not_found` ("Should not normally happen at least that you delete the tenant") · `method_not_found` ("You have requested a method that is currently not supported (should not happen)")
- **Structured field errors**: `field_required` — "A field is required to perform the operation (this errors has a field attribute with a code for the field: `otpCode`, `recoveryCode`)"
- **The one description that is actually user-facing recovery copy**: `pn_endpoint_disabled` — "We were unable to deliver the push notification after retrying many times. Try removing you account for the device and adding it again."

**Three patterns worth extracting.** The `feature_disabled` / `feature_disabled_by_admin` pair: when the same symptom has two different owners, ship two codes so the client can address the user to the right person. The four-way rate-limit split by scope (user vs tenant, SMS vs push): the remedy differs, so the code differs. And `(should not happen)` written into two descriptions: a code that exists for completeness is labelled as improbable, which tells an integrator not to build a UI branch for it.

**Quality defects in the Guardian table** `[observed]`, and they are numerous for a reference page: `"You don't have enought grants"` (enought) · `"You have exeed the amount"` ×4 (exeed) · `"Try removing you account for the device"` (you/your) · `"You not enrolled. Must enroll first"` (missing "are") · `"Should not normally happen at least that you delete the tenant"` (ungrammatical) · `"this errors has a field attribute"` · inconsistent terminal punctuation (some descriptions end with a full stop, most do not) · `otp` lowercase in one entry and `OTP` capitalised in another. Several descriptions are written in **second person addressed to the end user** ("You are already enrolled") while others are written in third person about the system ("The tenant associated cannot be found") — two registers in one table. This is a reference page that has not been copy-edited, and the strings in it are described by Auth0's own framing as material to "display informative messages", i.e. some of them will reach users verbatim.

### Self Change Password API errors `[observed]`

Three codes, each with a two-step resolution procedure: `invalid_request`, `invalid_user_password`, `change_password_error`.

The article's structure is worth recording because it is the Support Center's house template: `Overview` → `Applies To` → `Cause` → `Solution`, with the Solution split into one question-form heading per error: `How is the *invalid_request* error resolved?` · `How is the *invalid_user_password* error resolved?` · `How is the *change_password_error* resolved?`

**`Applies To` as a standing section** is the pattern to steal — a three-item scope list (`Auth0`, `Self Change Password API`, `Custom Database Connections`) that lets a reader confirm in two seconds whether the article is about their situation. It appears on every Support Center article harvested (`Auth0`, `Error Handling`, `Best Practices` on the error-handling page). And `Cause` as a separate section from `Solution` means the reader can stop after understanding, or continue to fixing.

Note the register slip: the third heading drops the word "error" (`How is the *change_password_error* resolved?`) where its two siblings keep it, because the code already contains "error" — correct reasoning, inconsistent result.

### Guidance to developers on their own error copy `[observed]`

From `Auth0 Error Handling Best Practices`, the section headed **"Why are meaningful error code descriptions necessary?"**:

> "The `UnauthorizedError` object only returns the supplied description. To use specific processing for unauthorized error conditions, format descriptions to include easily accessible error code information."

Auth0 is telling its customers that the platform's own error channel is a **single free-text string**, and therefore that the customer must encode their own machine-readable code inside the human-readable description. That is a candid admission of a content-architecture limitation, and the advice ("format descriptions to include easily accessible error code information") is the right workaround. The page also documents the two return shapes with their different consequences:

- `return callback(new Error('some description'));` — generic failure
- `return callback(new UnauthorizedError('some description'), user, context);` — "causes an `unauthorized` error condition with the supplied error description to return to the application that initiated authentication… This allows an application to offer conditional retry capability"

**"This allows an application to offer conditional retry capability"** is the key clause: the reason to use the specific error object is that it lets the *customer's* app decide whether to offer a retry. The error-code choice is framed as a UX-affordance choice, not a logging choice.

### The end-user-facing half `[documented]`, and it is deliberately thin

Auth0's public documentation describes what the end user sees almost entirely in the abstract:

- Breached-password signup: "you will receive an error message, preventing you from using the breached password."
- Breached-password login: "the user will receive an error message, preventing them from logging in **and advising to reset their password**."
- Breached-password reset: "the end-user will receive an error message, preventing them from resetting their password **and advising them to use another password**."

**Three failures, three different pieces of advice, and no verbatim string given for any of them.** The docs specify the *content requirement* ("advising to reset their password") without publishing the copy. That is consistent with the split this section is about: the developer-facing artefact is a named code, the user-facing artefact is a described intent, and the actual string is a tenant-level, localisable, customer-overridable asset (see the Custom Text API in T5/T13). **No user-facing error strings are quoted in this file because none were observed on a public surface.**

The default error page is described only by what the developer should do instead of using it: "If possible, you should host your own custom error page and configure Auth0 to use it instead of the default page. This allows you to provide more complete and customized explanations to users about what to do in the event of an error." Read closely, that is Auth0 saying its own default error page does **not** provide complete explanations — by design, because a shared multi-tenant error page cannot know the application's context or the tenant's risk posture.

### Recovery paths

**The unblock link in the notification email** `[documented]`: "By default, blocked account email notifications contain a link that allows the user to unblock their account." Self-service recovery from a security block, shipped by default, with the administrator able to remove it. Paired with the enumerated five-exit block lifecycle in T6.

**Rate-limit error with an HTTP status attached** `[documented]`: "once a request meets the brute force threshold, we respond to subsequent requests from the given user identifier with an **HTTP 429 `too_many_attempts` error**." Status code and string code given together.

**Support Center's seeded troubleshooting articles** `[observed]`: `Troubleshooting Rate-Limit Exceeded During Authentication` · `Password Reset Emails Not Received` · `"User Already Exists" Error When Creating New User` · `Request an MFA reset for my Auth0 account` · `Refresh Token and Session Management` · `How to Recover Admin Access to a Tenant`.

Four title shapes in six titles: gerund-initial (`Troubleshooting …`), noun-phrase-symptom (`Password Reset Emails Not Received`), quoted-error-string (`"User Already Exists" Error When Creating New User`), and first-person request (`Request an MFA reset for my Auth0 account`). `How to Recover Admin Access to a Tenant` is the one that matters most and it is the only one in `How to` form — **the total-lockout article for the administrator**, which is the identity product's own worst-case failure.

### Naming inconsistency in the error vocabulary itself — the headline defect `[observed]`

Auth0's error codes use **two incompatible naming conventions in one table**:

- `snake_case`: `invalid_password`, `password_strength_error`, `invalid_user_password`, `too_many_attempts`, `user_exists`, `mfa_invalid_code` … (26 of 28 codes across both tables, plus all 31 Guardian codes)
- `PascalCase`: `PasswordHistoryError`, `PasswordStrengthError` (2 codes, both in the login table)

Worse, **`PasswordStrengthError` and `password_strength_error` are semantically the same failure** — "The password provided does not match the connection's strength requirements" versus "The chosen password is too weak" — filed in different tables (login vs signup) under different casings. A developer writing a switch statement over password failures must handle both spellings of one concept.

This is a genuine, consequential content defect in the artefact that is this product's flagged strength. It almost certainly reflects two generations of Auth0's internal APIs; the reference page reproduces the archaeology rather than resolving or flagging it. Recorded as the most useful negative finding in this file.

## T9 Notifications & system messages

**Notification design is unusually well specified for a security product** `[documented]`

| Notification | Channel | Limit / frequency |
|---|---|---|
| Brute-force account blocked | SMS, "if they use a phone identifier in the login flow" | "maximum of 1 per hour per identifier" |
| Brute-force account blocked | Email, "if they have an email address associated with their account" | "maximum of 1 per hour per unique IP address" |
| Breached credential used | Email to user | "Throttled to once per hour per user" |
| Breached credential used | Email to tenant admins | "Throttled to once per hour per IP address" |
| `pwd_leak` log event | Tenant log | "Throttled to once per hour per IP address" |
| Account blocking itself | — | "No throttling applied. User accounts are always blocked when a compromised credential is detected." |

**The throttling table is the artefact to steal.** Four things are throttled, one thing explicitly is not, and each throttle names its own **key** (per identifier / per user / per IP address). Then the docs add the diagnostic consequence:

> "If you do not receive expected email notifications or do not observe `pwd_leak` events in your tenant logs, verify whether the detection occurred within the throttling period. During the throttling window, notifications and log events are suppressed, which is **expected behavior**. However, user account blocking always occurs regardless of throttling."

Auth0 documents the **absence of a notification as a designed outcome**, pre-empts the support ticket it would otherwise generate, and reasserts the safety property that is never throttled. "This is expected behavior" attached to a missing message, with the reason, is a pattern most products only produce after the incident.

**Notification frequency and its information trade-off, disclosed** `[documented]`:

> "Choose the notification frequency: **Immediately**, **Daily**, **Weekly**, or **Monthly**." … "If you choose **daily**, **weekly**, or **monthly**, your notification will include the number of breaches to your application. If you choose **immediate**, your notification will include the user account attempting to breach your application."

**Batched notifications get a count; immediate notifications get an identity.** The content of the message changes with its cadence, and the docs state which you lose. An administrator choosing "Weekly" is told, at the point of choosing, that they will no longer see *which account*. Naming what a preference costs you, in the preference's own help text, is directly transferable.

**Named email templates** `[documented]`: `Password Breach Alert` (selected from a `Template` dropdown at Branding > Email Templates). Related doc: `Customize Blocked Account Emails`. Auth0 names its security emails after the event, not after the action ("Password Breach Alert", not "Reset your password").

**Notification purposes are stated in one sentence each** `[documented]`: for breached credentials, "Send an email to the user when a login attempt happens. The email informs users about the risk and instructs them to change their password immediately." Two verbs — *informs* and *instructs* — which is the correct two-part job for a security notification and is worth naming explicitly in a content spec.

**Developer-facing system messaging** `[observed]`: a `Warning` admonition appears at the top of the Breached Password Detection page disclaiming legal/security/compliance advice — a long paragraph ending "Okta is not liable to you for any loss or damages that may result from your implementation of any recommendations in these materials." A liability disclaimer at the head of a *technical configuration page* is unusual and reflects Okta-era legal review; it pushes the actual content below a wall of hedging.

**Marketing-side notification copy** `[observed]`: "Protect and notify your users when credentials are leaked or during an attempted account takeover." The pricing add-on card for Attack Protection frames notification as half the product.

## T10 Disclosures, legal & compliance

**Plan-card disclosures use a footnote ladder** `[observed]`. The Free card carries two asterisked notes — "*credit card verification required for custom domains." and "**subject to system limitations." — and the Essentials/Professional cards carry a superscripted one: "¹ Upgrade to B2B to continue using EC, Self-Service SSO, and SCIM."

A downgrade-on-upgrade, disclosed in a footnote, using an unexpanded abbreviation (`EC`) that appears nowhere else on the page. Recorded as a defect with real commercial consequence for the reader.

Plus `learning.auth0.com` (courses and skill badges), `developer.auth0.com` (code samples, guides, events), `marketplace.auth0.com`, and `auth0.com/ai/docs` — **a separate docs site for the AI-agent product**, with its own `/intro/overview` path.

**The seam that matters: `/docs/troubleshoot/*` URLs now 302 to `support.auth0.com`.** `auth0.com/docs/troubleshoot/error-handling-best-practices` resolves to `support.auth0.com/center/s/article/auth0-error-handling-best-practices`; `auth0.com/docs/troubleshoot/troubleshoot-authentication-issues` resolves to the Support Center **home page**, not to an equivalent article. So the docs' troubleshooting branch has been migrated into a Salesforce KB, the old URLs are preserved as redirects, and at least one of those redirects has lost its target. Meanwhile `/docs/troubleshoot/customer-support/...` URLs are still used as live deep-links from the pricing table. **One URL prefix, two systems, one broken landing.**

The migration also costs register consistency. The same content in the two systems reads differently: docs pages are titled `Brute-Force Protection`, `Tenant Settings`; KB pages are titled `Auth0 Error Handling Best Practices`, `Auth0 Self Change Password API Errors` — **product-name-prefixed titles**, which is a search-optimised Salesforce KB convention and redundant on Auth0's own domain.

**The docs' own machine-readable index** `[observed]`. Every `.md` page opens with a block addressed to a non-human reader:

> "## Documentation Index — Fetch the complete documentation index at: https://auth0.com/llms.txt — Use this file to discover all available pages before exploring further."

Then a `>` blockquote one-line page abstract. Auth0 ships an `llms.txt` and, crucially, **a plain-`.md` twin of every documentation page at the same path plus `.md`** — so `…/tenant-settings` and `…/tenant-settings.md` are the same content in two renderings. Same pattern as DigitalOcean's `index.html.md`, arrived at independently.

**Inline glossary tooltips are the standout docs-architecture pattern** `[observed]`. Auth0's docs markup wraps first-use technical terms in a `<Tooltip>` component carrying three things: a one-sentence definition, a CTA (`View Glossary`), and a deep link to the glossary anchor (`/docs/glossary?term=Auth0+Dashboard`). ## T12 FAQs

**Placement**: accordion at the foot of `/pricing`, headed `Frequently asked questions`, with a two-sentence preamble that routes before it answers:

> "Can't find the question you're looking for? Post on our community forum to receive help from our developer support team and the community."
> "For enterprise questions, you can contact an expert."

**Routing by question *type* before the list, not after it.** The preamble splits the reader two ways — self-serve/community for technical, sales for enterprise — so someone who does not see their question never has to scroll the list. Most FAQ blocks put this after the accordion, where it only catches readers who have already failed.

**Structural notes.** Nine slots, eight substantive. A user would ask "what happens when I hit 25,000 users?" Recorded as a register slip in an otherwise user-voiced set.

## T14 Voice, tone & accessibility

**Person and tense.** Second person for the developer throughout docs ("you can configure", "Make sure your tenant has"). First-person plural for Auth0 in operational statements, and notably in the *mechanism* sentences of security features: "**we** apply the attack mitigation protections you have selected", "once a request meets the brute force threshold, **we** respond to subsequent requests… with an HTTP 429", "**Auth0 tracks** large security breaches". The company is a named actor at the moment it does something to the customer's users, which is the right place for it.

Third person for the end user, consistently — `the user`, `the end-user`, `the affected user`, `your users`. **Auth0 almost never addresses the end user**, because it does not own that relationship; the customer does. The one exception is the Guardian error table, where several descriptions are written in second person ("You are already enrolled, cannot enroll again") because those strings are destined for end-user display. The register break marks the audience change, accidentally but usefully.

**Recommendation strength is graded and the gradations are used consistently** `[documented]`:

- "We **strongly recommend** keeping brute-force protection enabled" · "we **strongly recommend** enabling v2"
- "Auth0 **recommends** validating user-provided data before submitting" · "Auth0 recommends that you **do not** skip end-user confirmation in these cases"
- "**If possible**, you should host your own custom error page"
- "**Be cautious** when using third-party JavaScript on your signup page"
- "use it **sparingly**"
- "**Whenever possible**, …"

Six strength levels, each attached to a consequence. `Auth0 recommends that you **do not**` with the negation bolded is the cleanest way to write a prohibition that is not enforced.

**Typed admonitions with distinct jobs** `[observed]`: `<Warning>` (legal disclaimer; irreversible or breaking behaviour; version prerequisites), `<Callout>` (informational, blue, `file-lines` icon), `<Callout icon="lightbulb">` (diagnostic tip), `<Card title="Before you start">` (prerequisites), `<Card title="Availability varies by Auth0 plan">` (entitlement gate). The entitlement card is a good idea executed as a reusable component: "Both your specific login implementation and your Auth0 plan or custom agreement affect whether this feature is available." **Two variables named** (implementation and plan) rather than a bare "may not be available on your plan".

**Security copy leads with the mechanism and does not dramatise** `[observed]`. Across the attack-protection pages there is no fear appeal, no statistic about breach costs, no urgency. "Auth0 tracks large security breaches that occur on major third-party sites. If Auth0 identifies that any of your users' credentials were part of a breach, the breached password detection security feature triggers. In response, Auth0 can: …" — three sentences, subject-verb-object, then a list of configurable responses. The only emotive word on the page is `bad actors`, and it is defined.

**Zero exclamation marks observed** in docs and KB. Marketing has none either, with one exception: the startups FAQ answer — "Yes, Auth0 and our network of partners want to see you succeed!" and "apply here!". Two exclamation marks, both in the startup-programme answer, both in a register that appears nowhere else on the site.

**Testability content as a voice choice** `[observed]`. Breached Password Detection publishes literal test credentials — "Any password starting with `AUTH0-TEST-` triggers Breached Password Detection for testing purposes", plus two specific test passwords (`Paaf213XXYYZZ`, `Paat739!!WWXXYYZZ`) — and then a three-flow verification procedure (signup / login / reset), each ending with the exact log query to confirm it worked (`type: "signup_pwd_leak"`). **Giving a developer a deterministic way to see the failure state they are shipping to users** is a documentation decision with direct content-design consequences: the developer can read their own error copy in situ.

**Accessibility content** `[observed]`

- **A WCAG instruction embedded in feature documentation** — the single best accessibility-content finding in this harvest: "For WCAG compliance, inputs must be programmatically linked to their error messages - for example, by using `aria-describedby="error-id"` and `aria-invalid="true"` - to ensure screen readers announce validation errors." Auth0 is telling customers building custom login fields **how to make their own validation errors announce**, with the exact attributes and the reason. Placed in the client-side-validation section where the developer is already writing the error markup, not in a separate accessibility appendix.
- `Accessibility` appears as a feature row in the pricing comparison table, `Included` on all plans.
- Docs screenshots are `Frame`-wrapped and most carry alt text describing the UI location rather than the content: "Dashboard Tenant Settings General Settings tab", "Dashboard Tenant Settings Advanced Tab Device Flow User Code Format", "An image showing the command-line interface for Partials." ## Transferable patterns

1. **Split the error vocabulary at the platform boundary, and document both halves.** Ship a granular developer-facing code set (`password_dictionary_error` vs `password_no_user_info_error` vs `password_strength_error`), keep the wire-level response deliberately ambiguous where it would otherwise confirm an account's existence (`invalid_user_password` = "username **and/or** password"), and publish a named setting that collapses the rest — `Use a generic response in public signup API error message` — **with the threat model, the adversary, and the suppressed code all named in the help text**. Condition: the vagueness must be at the boundary, not in the documentation; being more specific in docs than on the wire is the point.
2. **Split one error code in two when the symptom is shared but the owner differs.** `feature_disabled` ("contact the provider") versus `feature_disabled_by_admin` ("disabled by your admin"). The user's next action is different, so the code is different. Same logic drives the four-way `too_many_sms` / `too_many_pn` / `too_many_sms_per_tenant` / `too_many_pn_per_tenant` split.
3. **Give a configuration that is on-but-inert its own honest state name.** `Monitoring` appears automatically when attack protection is enabled with all responses off, rather than letting `Enabled` mislead. Transferable to fraud rules, content filters, firewall policies, and feature flags — anything with an enforce/observe/off axis.
4. **Inline glossary tooltips with a canonical, deep-linkable glossary.** Definition on hover, `View Glossary` CTA, `?term=` anchor. Define each term by contrast with its nearest neighbour where the neighbour is the thing readers confuse it with (`ID Token`: "Credential meant for the client itself, rather than for accessing a resource"). The highest-leverage technique available to any documentation set with a dense, jargon-heavy domain.
5. **Write toggle help text as `When enabled, <the resulting world>`.** Never describe the control; always describe the consequence. Applied across ~10 consecutive tenant settings, it eliminates the "does this label describe the on state or the action?" ambiguity entirely.
6. **Document the absence of a notification as expected behaviour, with its throttle key.** "Throttled to once per hour per IP address"… "During the throttling window, notifications and log events are suppressed, which is expected behavior. However, user account blocking always occurs regardless of throttling." Names what is throttled, by what key, what is never throttled, and pre-empts the support ticket.
7. **State what a notification-frequency choice costs you, at the point of choosing.** Batched alerts carry a count; immediate alerts carry an identity. Auth0 says so in the setting's own help text.
8. **Pair the journey moment with the business verb.** `Sign up`/`Convert`, `Login`/`Protect`, `Evaluation`/`Win`, `Onboarding`/`Accelerate` — the user's action and the buyer's outcome in one grid, with each panel's body opening on its own verb. Lets one page serve the implementer and the approver.
9. **Lead the pitch with the indignity, not the benefit.** "Stop burning sprints on custom SAML just to close a contract." Name the task, the cost unit, and the humiliating reason, in the reader's own words. Condition: requires genuine familiarity with the reader's working life; done badly it reads as presumption.
10. **Make the pricing table auditable.** Hyperlink ~50 of 60 feature rows to the documentation that defines them, and footnote every instance of "unlimited" to the page that quantifies the limit.
11. **Disclose the limits of the free protection.** "Typical detection time: Up to 7-13 months" / "Coverage: English only" for the included breach detection, beside "12-36 hours" / "200+ countries" for the add-on, with the mechanism of each explained. An upsell table that is also the truth.
12. **Publish deterministic test credentials for the failure state.** `AUTH0-TEST-*` triggers breach detection; here are two literal test passwords; here is the log query that confirms each of three flows blocked. A developer who can reproduce the error state on demand can actually read the error copy they are shipping.
13. **Put the WCAG instruction where the developer is writing the markup.** "inputs must be programmatically linked to their error messages - for example, by using `aria-describedby="error-id"` and `aria-invalid="true"` - to ensure screen readers announce validation errors." In the validation section, with the attributes and the reason. Not in an accessibility appendix.
14. **`Applies To` as a standing section on every troubleshooting article.** Three scope items let a reader confirm relevance in two seconds, before reading the cause.
15. **Route by question type before the FAQ list, not after it.** "Can't find the question you're looking for? Post on our community forum… For enterprise questions, you can contact an expert." Catches the reader who will not find their question, before they scroll.

- **No verbatim end-user-facing error string was found on any public surface.** This is a substantive finding, not only a gap: Auth0's user-facing strings are tenant-level, localisable, and customer-overridable via the Custom Text API, so they do not exist as fixed public copy. T7 records the *described* user-facing intent ("advising to reset their password") and explicitly marks that no strings were observed. **No user-facing error copy is invented in this file.**
- The Management API and Authentication API references (`/docs/api/...`) were not opened. Auth0's docs state that "the Management API Explorer shows Management API error codes below each call", so a further, larger per-endpoint error catalogue exists and is unharvested. The two error-code references captured here are the library-level and Guardian-level ones.
- **Not harvested**: `auth0.com/ai/docs` (the separate AI-agent documentation site), `auth0.com/security`, `security.okta.com`, `auth0.com/privacy`, `auth0.com/docs/glossary` (the canonical glossary — tooltip definitions were captured in situ instead), `community.auth0.com`, `learning.auth0.com`, `developer.auth0.com`, `marketplace.auth0.com`, `status.fga.dev`, `uptime.auth0.com`, the changelog, and all `/features/*` and `/platform/*` product pages.
- **Localisation not tested.** Six locales are offered; only `English` was observed. Whether the docs, error descriptions, or KB are localised — and whether the six-locale switcher covers the docs at all — is unverified.
- Accessibility findings on the Support Center's `javascript:void(0);` skip links and on logo-strip duplication are **suspected, not confirmed** — no ARIA attributes, CSS, or accessible-name computation were inspected. The `alt="undefined"` and `alt="[partials]"` findings are confirmed from the markup.
- The status page's per-region `Core Services` / `Supporting Services` groupings render their *headings* but not their member components in the server HTML, so the component-level status vocabulary for Auth0 is unharvested.
